## 学习目标

- 区分 `system`、`user`、`assistant` 三种消息
- 会用提示词五要素写出清晰、可执行的指令
- 会用少样本与结构化输出约束模型回答
- 会用 `temperature`、`max_tokens` 与流式输出控制结果

## 1.5 三种角色

<div class="v-compare">
  <div class="v-compare-item">
    <h4>system</h4>
    <p>设定模型的长期行为、身份与边界。例如“你是 Python 助教，只回答编程问题”。通常放在消息数组最前面。</p>
  </div>
  <div class="v-compare-item is-neutral">
    <h4>user</h4>
    <p>用户这一轮提出的问题或指令。每次调用至少要有内容，模型才知道要做什么。</p>
  </div>
  <div class="v-compare-item is-neutral">
    <h4>assistant</h4>
    <p>模型之前给出的回答。多轮对话时把它放回数组，模型才能看到自己说过什么。</p>
  </div>
</div>

| 角色 | 谁写的 | 作用 |
|-|-|-|
| `system` | 开发者 | 设定身份、规则与输出格式 |
| `user` | 用户 | 提出当前任务 |
| `assistant` | 模型 | 保存上一轮回答，维持上下文 |

## 1.6 多轮对话就是消息数组

```python
messages = [
    {"role": "system", "content": "你是简洁的 Python 助教，回答不超过三句话。"},
    {"role": "user", "content": "列表和元组有什么区别？"},
    {"role": "assistant", "content": "列表可变，元组不可变；列表用方括号，元组用圆括号。"},
    {"role": "user", "content": "那我什么时候用元组？"},
]
```

每次请求都把完整数组发过去。模型本身不记得上一轮，是你在替它保存历史。历史越长，输入 token 越多，成本和延迟也越高。

<div class="v-callout is-tip">
  <strong>system 管边界，user 管任务</strong>
  <p>把“不许编造”“只输出 JSON”这类规则放 system；把本次具体问题放 user。两者混在一起，模型更容易忽略边界。</p>
</div>

## 1.7 提示词五要素

一条可执行的提示词，至少写清五件事：

| 要素 | 写什么 | 常见问题 |
|-|-|-|
| 角色 | 模型以什么身份回答 | 只写“你是一个助手”，没有专业边界 |
| 任务 | 这次具体要完成什么 | 任务太大，例如“帮我写个总结” |
| 上下文 | 依据哪些资料、对话或数据 | 没给资料，却要求“只根据资料回答” |
| 约束 | 长度、语气、禁止事项、资料不足时怎么办 | 只写“尽量准确”，没有可执行标准 |
| 输出格式 | 纯文本、列表、JSON，包含哪些字段 | 只说“结构化”，没给字段名 |

### 案例：把模糊需求改成可执行提示词

场景：学员要把 20 条课程反馈整理成改进建议。

反例：

```text
帮我写个总结。
```

它没有角色、范围、长度和输出格式；“好一点”无法执行，模型还可能补充反馈里没有的内容。

改写后：

```text
你是课程助教。
任务：把下面的 20 条课程反馈总结成 3 条改进建议。
上下文：只使用我提供的反馈，不引用外部信息。
约束：每条建议不超过 40 字；反馈中没有提到的问题不要补充。
输出格式：
1. 建议：...
   依据：...
```

对照五要素：

| 要素 | 案例中的写法 | 作用 |
|-|-|-|
| 角色 | 你是课程助教 | 限定回答视角 |
| 任务 | 总结成 3 条改进建议 | 明确产出数量与形式 |
| 上下文 | 只使用我提供的反馈 | 划定信息来源 |
| 约束 | 每条不超过 40 字；不补充未提到的问题 | 控制长度、减少编造 |
| 输出格式 | 编号列表，含“建议”和“依据” | 让答案可检查、可追溯 |

“依据”这一项很关键：它迫使模型把建议和原始反馈对应起来，方便人工核对，也减少凭空发挥。

<div class="v-callout is-warn">
  <strong>提示词不是越长越好</strong>
  <p>堆形容词不会让模型更准确。把任务、依据、边界和输出格式写清楚，比反复强调“请认真回答”更有效。</p>
</div>

## 1.8 少样本与结构化输出

### 案例：工单分类

场景：售后系统要把用户留言分成物流、退款、账号、其他四类，并标出紧急程度。

只写一句“把工单分类”，属于零样本（zero-shot），模型可能返回：

> 这属于物流问题，建议优先处理。

人看得懂，程序却无法稳定解析。改成少样本 + JSON 契约：

```python
messages = [
    {
        "role": "system",
        "content": "你是工单分类器。只输出 JSON，不要解释。"
                   "字段：category（物流/退款/账号/其他）、"
                   "urgency（高/中/低）、reason（不超过 30 字）。"
                   "无法判断时 category 填“其他”。",
    },
    {"role": "user", "content": "我的订单三天没发货，请尽快处理。"},
    {
        "role": "assistant",
        "content": (
            '{"category": "物流", "urgency": "高", '
            '"reason": "三天未发货，影响收货"}'
        ),
    },
    {"role": "user", "content": "优惠券怎么用？"},
]
```

要求结构化输出时，要同时给出：

1. 字段名与类型；
2. 允许的枚举值；
3. 无法判断时返回什么；
4. 解析失败后的处理方式。

模型返回文本后，程序仍然要校验，而不是直接相信：

```python
data = json.loads(text)
if data.get("category") not in {"物流", "退款", "账号", "其他"}:
    raise ValueError("category 不在允许范围")
```

这个案例有四个教学点：示例定义输出形状；枚举值减少自由发挥；无法判断时有兜底；解析后仍要校验。

<div class="v-callout is-warn">
  <strong>示例不是越多越好</strong>
  <p>示例要覆盖典型、边界与无法判断的情况。十个相似示例不如“一个典型、一个边界、一个无法判断”。示例太长也会挤占上下文。</p>
</div>

## 1.9 参数与流式

| 参数 | 作用 | 建议 |
|-|-|-|
| `temperature` | 随机性，越高越发散 | 事实、工具调用、结构化输出用 `0` |
| `max_tokens` | 限制输出长度 | 按任务设上限，避免一次生成过长 |
| `top_p` | 另一种采样范围 | 通常只调 temperature，不同时调两个 |
| `stream` | 是否边生成边返回 | 聊天界面用流式，脚本批处理可关闭 |

```python
json={
    "model": model,
    "messages": messages,
    "temperature": 0,
    "max_tokens": 300,
}
```

流式响应是 SSE 事件流，每行以 `data:` 开头：

```python
response = requests.post(url, headers=headers, json=payload, stream=True)
for line in response.iter_lines():
    if not line:
        continue
    text = line.decode("utf-8")
    if not text.startswith("data:"):
        continue
    chunk = text[len("data:"):].strip()
    if chunk == "[DONE]":
        break
    delta = json.loads(chunk)["choices"][0]["delta"].get("content", "")
    print(delta, end="", flush=True)
```

流式只改变“什么时候看到文本”，不改变 token 总量。脚本里做判题、提取字段时，用非流式更简单。

## 1.10 提示词迭代

提示词不是一次写完就结束。可靠的做法是：

1. 固定 5–10 个评测任务；
2. 每次只改一个变量（角色、约束、示例或格式）；
3. 记录成功率和失败分类；
4. 保留提示词版本，避免越改越乱。

### 案例：工具选择从 40% 到 100%

场景：Agent 有 `get_weather` 和 `query_orders` 两个工具。用户问“北京今天天气”，模型却调用了 `query_orders`。

V1 的工具描述：

```text
get_weather: 查询天气。
query_orders: 查询订单。
```

描述太短，模型不知道什么时候该用哪个。V2 补上使用与禁用场景：

```text
get_weather: 查询城市天气与温度。用户问天气、气温、是否下雨时使用；
不要用于订单、退款、账号问题。
query_orders: 查询订单状态与物流。用户提供订单号，或询问发货、
退款进度时使用；不要用于天气。
```

V2 后模型选对工具，但常把 `city` 写成“北京”，导致查询失败。V3 再补参数示例与边界：

```text
get_weather 的 city 参数使用英文城市名，例如 beijing。
如果用户没有说城市，先追问城市，不要猜测。
```

假设用 5 个固定任务测试，示意结果如下：

| 版本 | 成功率 | 主要失败 |
|-|-|-|
| V1 | 2 / 5 | 天气问题被交给 `query_orders` |
| V2 | 4 / 5 | `city` 写成中文，工具返回找不到城市 |
| V3 | 5 / 5 | 无 |

这个案例说明：工具描述也是提示词。a04 会正式展开工具三要素，这里先建立一个意识——提示词工程不只写 system，也写工具名称、描述与参数说明。

| 现象 | 先改哪里 |
|-|-|
| 回答太散 | 加输出格式与长度约束 |
| 编造资料 | 加“只依据资料，不足时说没有找到” |
| 格式时对时错 | 加字段说明与一两个示例 |
| 忽略规则 | 把规则从 user 移到 system |
| 结果不稳定 | 降低 temperature，再检查示例是否矛盾 |
| 工具选错 | 补工具描述的使用/禁用场景与参数示例 |

后面 a16 会讲如何用评测集验证改动是否真的有效。

## 小结

- `system` 定边界，`user` 提任务，`assistant` 存历史；
- 提示词至少写清角色、任务、上下文、约束与输出格式；
- 少样本能稳定格式，但要覆盖典型与边界，不是越多越好；
- 工具调用与结构化任务用低 temperature，并设置 max_tokens；
- 提示词迭代要一次只改一个变量，用评测集对比效果。
