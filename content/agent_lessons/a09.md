## 学习目标

- 看懂一份轨迹 JSON 的结构
- 识别循环、工具误用与幻觉三类失败
- 用规则自动检查轨迹

## 3.9 轨迹是什么

轨迹（trajectory）是一次 Agent 执行的完整记录：模型想过什么、调用了哪些工具、看到了什么、最后回答什么。

```json
{
  "version": 1,
  "task_id": "a09-ReAct-weather",
  "model": "deepseek-chat",
  "steps": [
    {"type": "thought", "content": "需要查询北京天气"},
    {"type": "action", "tool": "get_weather", "arguments": {"city": "beijing"}},
    {"type": "observation", "content": "北京 26℃"},
    {"type": "finish", "content": "北京今天 26℃"}
  ],
  "final_answer": "北京今天 26℃，适合出行。"
}
```

- `version`：格式版本，当前为 `1`；
- `task_id`：必须与题目要求一致；
- `steps`：按时间顺序排列的步骤；
- `final_answer`：最终给用户的回答。

## 3.10 三类失败轨迹

| 模式 | 特征 | 例子 |
|-|-|-|
| 循环 | 同一工具与参数反复出现 | 连续 5 次 `search("北京天气")` |
| 工具误用 | 工具或参数与任务不匹配 | 用 `query_orders` 查天气 |
| 幻觉 | 最终答案没有观察支撑 | 观察是“没有找到”，答案却说“共 5 单” |
| 提前终止 | 没调用工具就给出事实性答案 | 没查天气却说“今天 26℃” |
| 无终止 | 步数持续增长 | 一直 thought，没有 action 或 finish |

## 3.11 用规则检查轨迹

平台把轨迹解析成结构化数据，再逐条检查规则：

| 规则 | 检查内容 |
|-|-|
| `required_tool` | 是否调用了某个工具，可要求参数键 |
| `tool_order` | 多个工具是否按顺序出现 |
| `max_steps` | 总步数是否超限 |
| `min_steps` | 是否少于最少步数 |
| `max_tool_calls` | 工具调用次数是否超限 |
| `forbidden_tool` | 是否调用了禁止工具 |
| `final_answer_contains` | 最终答案是否包含关键词 |
| `no_error_steps` | 是否出现 error 步骤 |

规则判定不运行 Agent，也不调用模型。它只检查可观察的信号：步数、工具名、参数键、最终文本。

## 3.12 导出 trajectory.json

在本机运行时，把每一步追加到列表，结束时写入文件：

```python
import json

trajectory = {
    "version": 1,
    "task_id": "a09-ReAct-weather",
    "model": model,
    "steps": steps,
    "final_answer": final_answer,
}

with open("trajectory.json", "w", encoding="utf-8") as f:
    json.dump(trajectory, f, ensure_ascii=False, indent=2)
```

提交前检查三件事：

1. `task_id` 是否与题目要求一致；
2. `steps` 是否按真实顺序记录，没有手工补写；
3. `observation` 是否来自工具真实返回。

<div class="v-callout is-warn">
  <strong>轨迹要来自真实运行</strong>
  <p>平台只校验结构与规则，无法验证轨迹是否真实。伪造轨迹能通过机器检查，但会在结业演示与抽查中暴露。</p>
</div>

## 小结

- 轨迹记录思考、行动、观察与最终答案；
- 循环、工具误用、幻觉、提前终止、无终止是常见失败模式；
- 规则检查只针对可观察信号，稳定、可解释、零成本；
- 轨迹必须来自真实运行，导出后先自查 task_id 与步骤顺序。
