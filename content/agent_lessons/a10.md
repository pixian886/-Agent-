## 学习目标

- 用 SQLite 保存对话历史
- 会按窗口裁剪消息，保留 system 与最近几轮
- 理解摘要与长期记忆的取舍

## 4.1 模型本身不记得

每次调用 LLM 都是独立的。模型不会自动记住上一轮，是你在请求里把历史消息带上，它才“看起来记得”。

记忆要解决两个问题：

1. 存哪里：会话结束后还能恢复；
2. 带多少：上下文窗口有限，不能无限追加。

## 4.2 用 SQLite 存消息

```python
import sqlite3

conn = sqlite3.connect("chat.db")
conn.execute("""
CREATE TABLE IF NOT EXISTS messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    role TEXT NOT NULL,
    content TEXT NOT NULL,
    created_at TEXT NOT NULL
)
""")
```

写入时带上会话 ID 与时间：

```python
from datetime import datetime

conn.execute(
    "INSERT INTO messages (session_id, role, content, created_at) VALUES (?, ?, ?, ?)",
    ("s-001", "user", "列表和元组怎么选？", datetime.now().isoformat(timespec="seconds")),
)
conn.commit()
```

`sessions` 与 `messages` 分表更清晰：一个会话有标题、创建时间；消息只负责内容与顺序。

## 4.3 窗口裁剪

```python
def load_recent(conn, session_id: str, limit: int = 10) -> list[dict]:
    rows = conn.execute(
        """
        SELECT role, content FROM messages
        WHERE session_id = ?
        ORDER BY id DESC
        LIMIT ?
        """,
        (session_id, limit),
    ).fetchall()
    rows.reverse()
    return [{"role": role, "content": content} for role, content in rows]
```

如果 system 消息单独存放，就在最前面拼回去：

```python
messages = [{"role": "system", "content": SYSTEM_PROMPT}] + load_recent(conn, "s-001", 10)
```

注意三点：

- 按 `id` 或时间倒序取，再反转，保证顺序正确；
- `limit` 要小于模型上下文能承受的消息量；
- 工具消息、检索片段也占 token，不能只算用户消息。

## 4.4 摘要与长期记忆

窗口只能保留近期内容。更早的信息有两种处理方式：

| 方式 | 做法 | 适用 |
|-|-|-|
| 摘要 | 让模型把旧对话压成几段要点 | 连续聊天、会议记录 |
| 检索 | 把旧消息存起来，按关键词或向量检索 | 长期助手、知识库 |

摘要本身也要花 token，而且可能丢细节。重要事实（用户偏好、订单号、结论）最好结构化保存，例如单独一张 `facts` 表，而不是全塞进摘要。

<div class="v-callout is-warn">
  <strong>不要把整段历史无限追加</strong>
  <p>上下文越长，成本越高、延迟越大，模型也更容易忽略中间内容。窗口与摘要都是工程手段，不是模型自带能力。</p>
</div>

## 小结

- 模型不记忆，历史由应用保存并随请求发送；
- SQLite 按会话存消息，取最近 N 条组成窗口；
- system 固定保留，旧消息可摘要或检索；
- 重要事实结构化保存，不要只依赖摘要。
