## 学习目标

- 把上下文当成有限预算
- 会按优先级裁剪、摘要与结构化上下文
- 知道哪些内容绝不能丢

## 5.1 上下文是预算，不是仓库

上下文窗口能容纳的 token 有限。system、工具定义、用户问题、检索资料、历史消息、工具结果，全都在抢同一块空间。

  </div>

上下文工程（context engineering）不是“写更长的提示词”，而是决定**什么该进来、什么该出去、以什么形式进来**。

## 5.2 优先级

从高到低：

1. **system 规则**：身份、边界、输出格式；
2. **当前任务**：用户这一轮的问题与约束；
3. **工具定义**：本次可能用到的工具，不要一次塞几十个；
4. **检索资料**：top-k 块与来源；
5. **近期历史**：最近几轮对话；
6. **旧历史与日志**：摘要或按需检索。

冲突时先保高优先级。例如上下文快满时，不要把 system 删掉去保留十轮闲聊。

## 5.3 三种压缩手段

| 手段 | 做法 | 代价 |
|-|-|-|
| 裁剪 | 只保留最近 N 条、top-k 块 | 可能丢早期细节 |
| 摘要 | 把旧内容压成要点 | 摘要本身耗 token，可能失真 |
| 结构化 | 用表格、字段、JSON 表达状态 | 需要设计 schema |

结构化往往最省 token。例如把“用户偏好”存成：

```json
{"language": "zh", "tone": "concise", "forbidden": ["编造数据"]}
```

比保留十轮“请简洁一点”“不要说谎”的对话更可靠。

<div class="v-callout is-tip">
  <strong>把稳定信息放 system，把变化信息放 user</strong>
  <p>长期规则不要每轮重复；本轮任务与临时资料放 user。这样更容易控制 token，也更容易排查。</p>
</div>

## 5.4 常见错误

- 把整篇文档塞进上下文，模型反而忽略关键段；
- 工具定义全量加载，几十个 schema 占掉大半预算；
- 历史只增不减，成本和延迟持续上升；
- 摘要越写越长，最后又变成新的负担；
- 删除 system 来腾空间，导致边界与格式失效。

<div class="v-callout is-warn">
  <strong>上下文超限不是突然发生的</strong>
  <p>每次请求前估算 token，按优先级裁剪。等 API 返回超限错误再处理，用户体验已经很差。</p>
</div>

## 小结

- 上下文是有限预算，需要主动分配；
- 优先级：system 与任务 &gt; 工具 &gt; 资料 &gt; 历史；
- 裁剪、摘要、结构化都是压缩手段；
- 稳定规则放 system，变化内容放 user。
