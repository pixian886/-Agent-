## 学习目标

- 掌握 8 类轨迹规则
- 会为一类任务组合规则
- 知道规则判题与 LLM-as-Judge 的取舍

## 6.5 八类规则

| 规则 | 检查 | 典型用途 |
|-|-|-|
| `required_tool` | 是否调用某工具，可要求参数键 | 必须查天气才能回答 |
| `tool_order` | 工具是否按顺序出现 | 先检索再读取 |
| `max_steps` | 总步数上限 | 防止循环 |
| `min_steps` | 总步数下限 | 防止跳过工具直接回答 |
| `max_tool_calls` | 工具调用次数上限 | 控制成本与重复调用 |
| `forbidden_tool` | 禁止工具 | 安全场景禁止删除 |
| `final_answer_contains` | 最终答案关键词 | 必须包含真实结果 |
| `no_error_steps` | 不得出现 error 步骤 | 工具失败应作为观察处理 |

规则只看轨迹里的可观察信号：步骤类型、工具名、参数键、顺序、最终文本。它不执行 Agent，也不调用模型。

## 6.6 怎么组合规则

以“查询订单并回答”为例：

```json
[
  {"type": "required_tool", "tool": "query_orders", "args": ["date"]},
  {"type": "tool_order", "tools": ["query_orders"]},
  {"type": "min_steps", "value": 4},
  {"type": "max_steps", "value": 7},
  {"type": "max_tool_calls", "value": 2},
  {"type": "no_error_steps"},
  {"type": "final_answer_contains", "value": "2 单"}
]
```

- `min_steps` 防止模型不查工具直接编答案；
- `max_steps` 防止循环；
- `max_tool_calls` 控制成本；
- `final_answer_contains` 把答案与真实结果绑定；
- `no_error_steps` 要求错误以 observation 形式处理。

## 6.7 规则判题与 LLM-as-Judge

<div class="v-compare">
  <div class="v-compare-item">
    <h4>规则判题</h4>
    <p>稳定、可解释、零调用成本。只能检查结构信号，无法判断答案是否“写得好”。</p>
  </div>
  <div class="v-compare-item is-neutral">
    <h4>LLM-as-Judge</h4>
    <p>能评价相关性、语气、完整性。但结果受提示词与模型影响，成本更高，也可能被注入。</p>
  </div>
</div>

优先级：能用规则检查的，先用规则；规则覆盖不了的（例如“回答是否清晰”），再补 LLM 评审。不要让 LLM-as-Judge 成为唯一验收手段。

## 6.8 写规则的建议

1. 规则从真实失败案例来，不要凭想象堆；
2. 一条规则只检查一件事，失败信息要具体；
3. 关键词选择要能区分真假，例如用“3 单”而不是“3”；
4. 规则过多会让正常轨迹难以通过，先覆盖关键风险；
5. 规则要随任务变化维护，不是写完就不动。

<div class="v-callout is-warn">
  <strong>规则不能证明轨迹真实</strong>
  <p>规则只能检查 JSON 结构。伪造轨迹能通过规则，所以结业项目要配合现场演示与代码抽查。</p>
</div>

## 小结

- 8 类规则覆盖工具、顺序、步数、答案与错误；
- 规则组合要围绕真实失败设计；
- 规则优先，LLM-as-Judge 只补规则覆盖不了的部分；
- 规则无法验证轨迹真实性，需要演示与审查配合。
