## 学习目标

- 比较手写循环与 Agent 框架
- 知道 LangGraph、AutoGen 的定位
- 能判断什么时候该用框架

## 7.9 手写还是框架

<div class="v-compare">
  <div class="v-compare-item">
    <h4>手写循环</h4>
    <p>代码少、依赖少、每一步都看得见。适合学习、简单任务与需要完全控制流程的场景。</p>
  </div>
  <div class="v-compare-item is-neutral">
    <h4>Agent 框架</h4>
    <p>提供状态、编排、持久化、流式与可观测性。适合复杂流程与长期维护，但学习成本更高。</p>
  </div>
</div>

手写 ReAct 循环通常几十行就能跑通。框架的价值不在“替你写循环”，而在状态管理、断点恢复、并行编排与调试工具。

## 7.10 两个常见框架的定位

| 框架 | 更擅长 | 典型场景 |
|-|-|-|
| LangGraph | 图结构编排、状态、检查点、人机协同 | 多步骤、可恢复的长流程 |
| AutoGen | 多 Agent 对话与协作 | 角色对话、研究型任务 |

具体 API 会变化，选型时看三件事：是否需要持久化、是否需要复杂分支、是否需要可观测与回放。

## 7.11 什么时候用框架

适合用框架：

- 流程有分支、循环、并行，手写状态机开始难维护；
- 需要断点恢复、人工审批、长时间运行；
- 需要现成的 trace、回放与评测集成；
- 团队已有框架经验。

适合手写：

- 学习原理、课程练习；
- 单一循环、少量工具；
- 需要精确控制每一次模型与工具调用；
- 不想引入额外依赖与版本风险。

<div class="v-callout is-tip">
  <strong>先手写一遍，再用框架</strong>
  <p>手写过 ReAct 循环，才知道框架替你做了什么、出问题时该看哪里。直接上框架，排错会变成黑盒猜测。</p>
</div>

## 7.12 选型不要只看热度

- 先写清任务：步骤是否固定、是否需要恢复、是否多角色；
- 再看框架是否真的解决这些问题；
- 评估依赖、版本、部署与团队熟悉度；
- 用同一组评测任务比较手写与框架版本。

框架不是能力证明。能稳定通过评测、成本可控、可排错，才是可交付。

## 小结

- 手写循环简单可控，适合学习与小任务；
- 框架擅长状态、编排、持久化与可观测；
- LangGraph 偏图编排，AutoGen 偏多 Agent 对话；
- 先手写理解原理，再按任务复杂度选框架。
